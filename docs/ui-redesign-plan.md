# UI Redesign Plan

## Overview

Replace the current single-scrolling-column layout with a **card-based dashboard**
where every section is a self-contained card. Cards live on one seamless surface.
Each card shows a compact summary by default; clicking a card expands it to fill the
viewport with full detail. Right-clicking an expanded card (or pressing Escape)
returns to the dashboard.

Transitions should feel fluid and dynamic — CSS `transform` + `transition` rather
than page navigations.

---

## Architecture Decisions

### Framework: React + Vite ✓ (selected)

| Approach                    | Pros                                                                                | Cons                                                         |
| --------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Vanilla JS (current)        | Zero build step; single embedded binary; no npm                                     | Growing complexity; manual re-renders; poor state management |
| React via CDN (no build)    | Declarative state; no build step                                                    | CDN dependency; JSX needs Babel shim; no tree-shaking        |
| **React + Vite (selected)** | **Full ecosystem; fast HMR; JSX; hooks; clean component model; tree-shaken bundle** | **Requires npm and a build step**                            |
| Preact via CDN              | Tiny (~4 kB); React-compatible                                                      | Smaller community; no build = no JSX without shim            |

**Decision:** React + Vite. A build step is acceptable and gives the best long-term
developer experience. The compiled output is written to `internal/api/static/` and
embedded in the Go binary unchanged. No Node.js is required at runtime.

### Source layout

React source lives under a top-level `web/` directory. Vite builds into
`internal/api/static/` which is the path already embedded by `go:embed`.

```
web/                          ← React source (not embedded)
  package.json
  vite.config.ts
  tsconfig.json
  src/
    main.tsx                  ← ReactDOM.createRoot entry point
    App.tsx                   ← dashboard grid + card expand state
    cards/
      RunCard.tsx
      HistoryCard.tsx
      SettingsCard.tsx
    components/
      DriveRow.tsx
      ProgressBar.tsx
      HistoryTable.tsx
      Charts.tsx              ← Chart.js wrappers
      CompareModal.tsx
    lib/
      api.ts                  ← all fetch helpers
      sse.ts                  ← SSE connection hook
      format.ts               ← bytes, durations, dates
    styles/
      tokens.css              ← design tokens (--bg, --accent, …)
      cards.css               ← card grid, expand/collapse animation
      components.css          ← tables, badges, progress bars, toasts

internal/api/static/          ← Vite build output (committed / generated)
  index.html
  assets/
    index-[hash].js
    index-[hash].css
```

The `internal/api/static/` tree is committed so that the Go binary can be built
without Node.js (e.g. on a fresh machine running only `go build`). It is
regenerated by `make ui` or as part of `make build`.

## Build Integration

### Makefile

New and modified targets:

```makefile
NODE        := node
NPM         := npm
WEB_DIR     := ./web
STATIC_DIR  := ./internal/api/static

## ui: install npm deps and build the React frontend
ui:
	cd $(WEB_DIR) && $(NPM) ci
	cd $(WEB_DIR) && $(NPM) run build

## ui-dev: start the Vite dev server (proxies /api to :8080)
ui-dev:
	cd $(WEB_DIR) && $(NPM) run dev

## build: build React frontend then compile Go binary
build: ui
	@mkdir -p $(OUTPUT_DIR)
	CGO_ENABLED=0 $(GO) build $(GOFLAGS) -ldflags "$(LDFLAGS)" \
		-o $(OUTPUT_DIR)/$(BINARY) $(CMD_DIR)
	@echo "Built $(OUTPUT_DIR)/$(BINARY) (version=$(VERSION))"

## build-go: compile Go binary only (skips frontend build, uses committed static/)
build-go:
	@mkdir -p $(OUTPUT_DIR)
	CGO_ENABLED=0 $(GO) build $(GOFLAGS) -ldflags "$(LDFLAGS)" \
		-o $(OUTPUT_DIR)/$(BINARY) $(CMD_DIR)

## dev: build frontend + Go binary and run the web UI locally at :8080
dev: build
	$(OUTPUT_DIR)/$(BINARY) -web -addr :8080

## clean: remove build artefacts (does NOT wipe internal/api/static/)
clean:
	rm -rf $(OUTPUT_DIR) coverage.out coverage.html

## clean-ui: wipe the generated static assets (use before a full rebuild)
clean-ui:
	rm -rf $(STATIC_DIR)/assets $(STATIC_DIR)/index.html
```

The original `build` target becomes `build-go` for the fast path (no Node).
The new `build` runs `ui` first so CI always ships a fresh frontend.

### Dockerfile

Split into three stages:

```dockerfile
# ── Stage 1: build React frontend ───────────────────────────────────────────
FROM node:22-alpine AS ui-builder

WORKDIR /web
COPY web/package.json web/package-lock.json ./
RUN npm ci
COPY web/ ./
RUN npm run build          # output → /web/dist

# ── Stage 2: build Go binary ─────────────────────────────────────────────────
FROM golang:1.24-alpine AS go-builder

RUN apk add --no-cache git ca-certificates
WORKDIR /src

COPY go.mod go.sum ./
RUN go mod download

COPY . .
# Overwrite static/ with the freshly built frontend
COPY --from=ui-builder /web/dist ./internal/api/static/

RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -trimpath -ldflags="-s -w" \
    -o /out/bit-rot-detector \
    ./cmd/bit-rot-detector

# ── Stage 3: minimal runtime image ───────────────────────────────────────────
FROM scratch

COPY --from=go-builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=go-builder /out/bit-rot-detector /usr/local/bin/bit-rot-detector

USER 65534:65534
ENTRYPOINT ["/usr/local/bin/bit-rot-detector"]
```

Key points:
- Node.js and all npm artefacts are isolated to the `ui-builder` stage; nothing
  leaks into the runtime image.
- The `go-builder` stage copies the Vite output directly into `internal/api/static/`
  before `go build`, so the embedded assets are always current.
- The final `scratch` image is unchanged — still a single static binary with no OS.
- `.dockerignore` should exclude `web/node_modules` and `web/.vite` to avoid
  copying them into the build context.

### .dockerignore additions

```
web/node_modules
web/.vite
web/dist
```

(`web/dist` is excluded from the build context because `ui-builder` regenerates it
inside Docker; the version committed to the repo is only for Go-only builds.)

```
┌────────────────────────────────────────────────────────┐
│  Header: logo · title · version · global status dot    │
├──────────────┬──────────────┬──────────────────────────┤
│  Run Card    │ History Card │   Settings Card           │
│  (1/3 width) │ (1/3 width)  │   (1/3 width)            │
└──────────────┴──────────────┴──────────────────────────┘
```

Grid is responsive: 3 columns on wide viewports → 2 → 1 on narrow screens.

When any card is expanded it occupies the full viewport with a subtle backdrop
dimming the rest of the dashboard.

## Cards

### Run Card

**Collapsed (summary)**

```
┌─────────────────────────────────┐
│  ▶ Last Run                     │
│  State: ● OK          2 drives  │
│  Duration: 1m 23s               │
│  Started: Feb 23 14:05          │
│  Files scanned: 48,231          │
└─────────────────────────────────┘
```

**Expanded (full screen)**

- Live progress bar + phase badges (Walk / Hash / Scrub) when running
- Per-drive rows, each with:
  - Drive name, path, type badge (HDD/SSD), SMART badge
  - Stat grid: Scanned / Added / Modified / Removed / Validated / Corrupted
  - Disk-usage bar with warn/error thresholds
  - Expandable corrupted-file list
  - Error box (if applicable)
  - Sync and Scrub buttons
- Toolbar: Sync All · Scrub All · Refresh · Export CSV · Export JSON
- Failures panel (appears when errors exist)

**Refresh behaviour:**
Charts and stats re-render automatically on `done` SSE event. The status-poll loop
(every 30 s) also triggers a redraw. No manual Refresh press is needed.

### History Card

**Collapsed (summary)**

```
┌─────────────────────────────────┐
│  📈 History                     │
│  30 runs in index               │
│  [spark line: file-change trend]│
│  Last corruption: never         │
└─────────────────────────────────┘
```

Spark line is a tiny `<canvas>` (no labels, no axes) rendering `files_added` and
`files_corrupted` for the last 30 runs as an overlay.

**Expanded (full screen)**

- Full-size **Combined Files + Corruption** stacked line chart (auto-refreshes after sync/scrub)
- Full-size **Run Duration** bar chart with Show Sync / Show Scrub toggles
  (visibility persisted in `localStorage`)
- **Run history table** (sortable, most-recent first):
  Drive · Started · Duration · Scanned · Added · Modified · Removed · Validated · Corrupted
  - Corrupted count shown in red when > 0
  - Multi-select two rows → Compare button → diff modal overlay
- **Corruption drill-down panel** (shown only when non-empty):
  Drive · Run ID · Detected · Files Corrupted

### Settings Card

**Collapsed (summary)**

```
┌─────────────────────────────────┐
│  ⚙ Settings                    │
│  Next scheduled: daily @ 03:00  │
│  Notify on: corruption, errors  │
│  Disk warn: 75%  error: 90%     │
└─────────────────────────────────┘
```

**Expanded (full screen)**

Sections:

1. **Configuration file** — read-only view of parsed env/config values
   (TARGET_DIRECTORY, SCRUB_SCHEDULE, SMTP_*, etc.) with edit capability
   where the backing store allows runtime changes.

2. **Disk thresholds** — warn % and error % inputs, Save button.

3. **Notification rules** — On Success / On Warning / On Corruption / On Error
   checkboxes, Save button, Test Email button.

4. **Schedule** — table of schedule entries; each row: Enabled toggle · Label ·
   Cron expression · Save. Supported: `@hourly`, `@daily`, `@weekly`, `HH:MM`.

5. **Config parser / editor** *(new)* — displays all config keys sourced from the
   environment or config file. For keys that can be mutated at runtime, shows an
   inline text input with a Save button. Read-only keys are shown greyed out.
   Changes POST to a new `POST /api/config` endpoint and take effect without restart
   where possible (settings-backed values); restart-required keys show a warning
   banner.

## Expand / Collapse Interaction Model

| Gesture                      | Effect                       |
| ---------------------------- | ---------------------------- |
| Click card                   | Expand card to full viewport |
| Right-click expanded card    | Collapse back to dashboard   |
| Press `Escape`               | Collapse back to dashboard   |
| Click backdrop (dimmed area) | Collapse back to dashboard   |

Animation:
- Expanding: card scales up from its grid position to `100vw × 100vh` using CSS
  `transform: scale()` + `transition: transform 0.3s ease, border-radius 0.3s ease`.
  FLIP technique (First-Last-Invert-Play) ensures smooth origin-aware animation.
- Collapsing: reverse.
- Background cards blur slightly (`filter: blur(2px)`) while one is expanded.

Only one card can be expanded at a time.

## Chart Auto-Refresh

Currently charts are drawn once on page load. Proposed:

1. On `done` SSE event, call `refreshHistory()` which re-fetches
   `GET /api/history?limit=30` and calls `chart.data.datasets[n].data = …` +
   `chart.update('active')` on each Chart.js instance.
2. The status-poll loop (30 s) also triggers `refreshHistory()` if the last
   completed-run timestamp has changed.
3. No full page reload; charts animate to new values via Chart.js transitions.

## Config Architecture

### Split: secrets vs. configurable settings

| Source                   | What lives here                  | Writable at runtime?                       |
| ------------------------ | -------------------------------- | ------------------------------------------ |
| **Environment / `.env`** | `SMTP_USERNAME`, `SMTP_PASSWORD` | No — restart required                      |
| **`config.yaml`**        | Everything else (see below)      | Yes — `POST /api/config` rewrites the file |

The `.env` file shrinks to secrets only. All other settings migrate from env vars
and from the current JSON `settings` store into a single `config.yaml`.

### config.yaml schema

```yaml
# Paths to monitor (required)
target_paths:
  - /mnt/nas
  - /mnt/backup

# SMTP (non-secret fields only; credentials come from env)
smtp:
  host: mail.smtp2go.com
  port: 587
  sender: alerts@example.com
  recipient: you@example.com

# Scrub behaviour
scrub_percentage: 1.0          # 0.1–100.0
scrub_frequency: daily         # daily | weekly | monthly

# Worker pool
max_workers: 4

# Logging
log_level: INFO                # DEBUG | INFO | WARN | ERROR
log_retention_days: 7

# Disk-usage alert thresholds (UI settings)
disk_thresholds:
  warn_pct: 75
  error_pct: 90

# Per-event email notification toggles (UI settings)
notification_rules:
  on_success: false
  on_warning: true
  on_corruption: true
  on_error: true

# Scheduled auto-runs (UI settings)
schedule:
  - label: Daily sync
    cron_expr: "@daily"
    enabled: true
  - label: Weekly scrub
    cron_expr: "@weekly"
    enabled: true
```

### Backend changes

1. **Add dependency** `gopkg.in/yaml.v3`.
2. **Refactor `internal/config/config.go`**
   - Replace env-var parsing with YAML unmarshal into a `Config` struct with
     `yaml:"..."` tags.
   - `Load(path string) (*Config, error)` — reads file; if absent, writes defaults
     and returns them so first run is zero-config.
   - `Save(cfg *Config, path string) error` — marshal and atomically write (write
     to a temp file then `os.Rename`).
   - After loading YAML, overlay secrets from env:
     `cfg.SMTP.Username = os.Getenv("SMTP_USERNAME")`
     `cfg.SMTP.Password = os.Getenv("SMTP_PASSWORD")`
   - Secrets are **never** included in marshalled output.
3. **Remove `internal/settings` package** — all fields (`DiskThresholds`,
   `NotificationRules`) are now top-level keys in `Config`. Callers that used
   `settings.Store` call `config.Store` instead.
4. **Move schedule entries** from the scheduler package into `Config.Schedule`;
   scheduler reads them from the live config store.
5. **Update `internal/api/server.go`**
   - `POST /api/settings` → `POST /api/config` (saves YAML, updates in-memory store).
   - `POST /api/schedule` → updates `Config.Schedule` and saves YAML.
6. **`.env.example`** — retain only `SMTP_USERNAME` and `SMTP_PASSWORD` (with
   comments explaining all other settings live in `config.yaml`).
7. **Add `config.yaml.example`** showing all non-secret keys with comments.
8. **Update `internal/api/server.go` `GET /api/config`** — returns the full
   in-memory config minus `SMTP.Username` and `SMTP.Password` (redacted).

### Secret redaction rule

Fields tagged `yaml:"-"` are never serialised to YAML. The API response struct
for `GET /api/config` omits them entirely (`json:"-"`).

```go
type SMTPConfig struct {
    Host      string `yaml:"host"      json:"host"`
    Port      int    `yaml:"port"      json:"port"`
    Sender    string `yaml:"sender"    json:"sender"`
    Recipient string `yaml:"recipient" json:"recipient"`
    // Secrets: loaded from env, never written to disk or returned by API
    Username  string `yaml:"-" json:"-"`
    Password  string `yaml:"-" json:"-"`
}
```

## Config Parser & Editor (new feature)

**Backend changes required:**

- `GET /api/config` — returns the full `Config` struct serialised to JSON, with
  `SMTP.Username` and `SMTP.Password` redacted (`"***"`).
- `POST /api/config` — accepts a partial or full config JSON body; merges into the
  in-memory store and atomically saves `config.yaml`; overlays secrets from env
  after save.
- All YAML keys are editable via the API. Secret env vars (`SMTP_USERNAME`,
  `SMTP_PASSWORD`) are shown read-only in the UI with a `Set via env` badge and are
  never submitted in POST bodies.
- `target_paths` changes require a restart; the UI shows a warning banner when this
  key is edited.
